II. Testing Documentation
1. Scope of Testing
Target of test: the PrintGrid platform - a distributed 3D printing fulfillment and scheduling system. The scope covers the features implemented in the MVP and the extended scope, verified at unit, integration and system level.
In scope:
* Customer module: registration and authentication (FR-CUST-001), 3D model upload and validation (FR-CUST-002/004), in-browser 3D preview (FR-CUST-003), print configuration (FR-CUST-005), quoting and order placement (FR-CUST-006/007), staged payment and refunds (FR-CUST-008/012), personal model library (FR-CUST-010).
* Scheduling and assignment (core): geometry analysis and slicing (FR-SCHED-001/002), capability filtering (FR-SCHED-003), multi-criteria scoring (FR-SCHED-004), quote-time speculative scheduling (FR-SCHED-005), job placement (FR-SCHED-006), event-driven rescheduling (FR-SCHED-007), calibration (FR-SCHED-008) and the assignment decision log (FR-SCHED-009).
* Lab module: registration and approval (FR-LAB-001), machine registry (FR-LAB-002), material inventory (FR-LAB-003), job accept/decline (FR-LAB-004) and the production workflow including QC proof and handover (FR-LAB-005).
* Hub module: batch receipt (FR-HUB-001), quality inspection (FR-HUB-002), reprint management (FR-HUB-003), order consolidation (FR-HUB-004) and shipping with delivery confirmation (FR-HUB-005).
* Admin: accounts and RBAC (FR-ADMIN-001), runtime configuration (FR-ADMIN-002) and shared catalogues (FR-ADMIN-003).
Non-functional scope: quote generation under 60 s (NFR-PERF-001), rescheduling under 30 s (NFR-PERF-002), API median latency under 500 ms (NFR-PERF-003), 100 concurrent users (NFR-PERF-005), correctness and determinism of the scheduling computation, and ownership isolation between customers.
Out of scope: automated UI testing (Selenium/Cypress), load testing beyond 100 concurrent users, penetration testing and security audit, accessibility certification, and browser coverage beyond Chrome, Firefox and Edge. Payment is exercised against the SEPay sandbox/bridge only; no real money moves during testing.

2. Test Strategy
2.1 Testing Types
1. Unit Testing
* Objective: verify a single unit (domain entity, command handler, validator, algorithm function) in isolation.
* Technique: xUnit + NSubstitute (mock repositories and unit of work) + FluentAssertions; Arrange-Act-Assert.
* Completion criteria: 100% of unit cases pass; core domain line coverage = 80%.
2. Integration Testing
* Objective: verify that modules work together - Web API endpoint ? MediatR handler ? EF Core ? PostgreSQL, including JWT authentication and authorization.
* Technique: WebApplicationFactory against a real PostgreSQL test database; seed data is created through EF; every flow is exercised through the real pipeline.
* Completion criteria: all integration flows create/read/update correctly; cross-tenant access returns 404; unauthenticated access returns 401.
3. System Testing (end-to-end)
* Objective: verify complete user journeys across the running frontend, backend and database against the demo script.
* Technique: manual and scripted flows through the live application; API-level regression through Swagger/Postman.
* Completion criteria: the demo script (register ? login ? upload ? configure ? quote ? order ? track ? logout) passes with 0 critical defects.
4. Security Testing (targeted)
* Objective: confirm ownership isolation and authentication enforcement.
* Technique: cross-user API calls (user B cannot read, update or delete user A's models or orders), unauthenticated calls, invalid or rotated refresh tokens, role checks on admin endpoints.
* Completion criteria: cross-tenant access returns 404, unauthenticated access returns 401, forbidden roles return 403.
5. Performance and Timing Testing (targeted)
* Objective: verify the scheduling and API timing targets in scope.
* Technique: benchmark scheduling runs at network sizes of 10, 25 and 50 labs; measure API latency under a basic load.
* Completion criteria: quote under 60 s; reschedule under 30 s (average under 15 s); API median under 500 ms.
6. Regression Testing
* Objective: ensure new changes do not break existing behaviour.
* Technique: rerun the full unit and integration suites plus the end-to-end demo script before each sprint review and before the feature freeze.
* Completion criteria: no critical or high defect reopened; 0 regression in the core scheduling paths.

The core scheduling and assignment engine is the strongest verified area: capability filtering, weighted scoring, quote-time placement, event-driven rescheduling and the decision log are covered by dedicated unit tests and by an integration flow that exercises the real PostgreSQL pipeline, including the EXCLUDE constraint that prevents double-booking.
Authentication and ownership isolation are the second strongest area. Cross-tenant reads, updates and deletes return 404, unauthenticated calls return 401 and admin endpoints enforce RBAC. This is both a demo-critical and a security-critical property.
No critical or high defect remains open. The eight defects found during the project are fixed and closed, and each fix is covered by a regression case. The five pending system cases are manual UI checks (3D preview, print configuration, admin screens) and one SEPay sandbox check; they are scheduled for the final acceptance round and are not blockers for the demo.
Residual risk is concentrated in the out-of-scope areas: real payment settlement, real lab hardware and load beyond 100 concurrent users. Within the declared scope, the system is ready for the acceptance demo against 13-Acceptance-Criteria.md.
